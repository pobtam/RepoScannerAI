What this program is made of, and how a finding travels through it

A guide to the pieces, what each one does, and how information moves between them — written for a reader who is not a programmer.

It describes what is actually in this repository, read from the code rather than from the design documents. Where the code and a specification disagree, the code wins and the difference is noted.

Words used throughout

Repository
Often shortened to repo. One codebase. A company might have dozens or hundreds.
Finding
One security problem in one repository. “This repository uses a library version with a known flaw” is a finding.
Run
One pass over the fleet of repositories. Think of it as one inspection round.
Fleet
All the repositories the program watches.
Pull request
A proposed change to a codebase that a person reviews and approves before it takes effect.

01One-paragraph summary

This program watches a set of codebases for security problems, decides which ones matter, and where it safely can, proposes the fix itself as a change for a human to approve. It runs a round of inspections, collects what nine different inspection tools report, merges duplicate reports of the same problem into one, adds outside context about whether that problem is being exploited in the real world, scores it, and applies a written policy to decide what to do: fix it automatically, raise a ticket for a person, escalate it, or wait for someone else to fix the shared component it lives in. It then proves its own work by re-inspecting: a problem counts as resolved only when a successful inspection can no longer find it, not when a fix was merged. Everything it could not do is reported as loudly as everything it did — which repositories failed to be inspected, which numbers rest on missing information, and which findings disappeared for reasons nobody has established. The last part is the unusual one: the program is built so that no number is ever shown without stating what it rests on.

02The pieces

Each entry gives the name you would search for in the code, a plain sentence about its job, and what goes in and comes out.

The vocabulary

internal/model

The dictionary

Defines the words the whole program uses — what a finding is, the thirteen states it can be in, the reasons it can be stuck, and the rules for moving between states. It also holds the shared definition of “this text looks like a password”, which several other pieces use to refuse to print one.

Takes in
Nothing. It is the dictionary.
Puts out
The shapes and rules everything else is built from.

internal/fingerprint

Stable identity

Gives every finding a stable identity, so the same problem found twice is recognised as one thing, and a genuinely different problem is recognised as new.

It builds that identity from the repository, the kind of problem, the vulnerability’s identifier, and the location — deliberately not the line number, so reformatting a file does not make the program think a new problem appeared.

Takes in
One raw report from an inspection tool.
Puts out
A short identifier, e.g. 1be7a0a5488737ec.

Looking at the code

internal/scan · scan/adapters · scan/runner

Inspection

Runs the inspection tools against a copy of a repository and translates each tool’s output into the program’s own vocabulary. There is one small translator (an adapter) per tool — nine of them.

Two things it does that matter later. If a tool crashes, that becomes a recorded gap in coverage, not a failed inspection — the other tools’ results still count, and the missing one is named. And it reads the repository’s own list of dependencies (its go.mod file), which is what later makes it possible to say “eleven other repositories use this same component”.

Takes in
A copy of a repository, and the list of which tools apply to it.
Puts out
A list of raw findings, a list of coverage gaps, the dependency list, and which tools succeeded and which failed.

Remembering

internal/store

Memory

The memory of the whole system. It holds every finding, every inspection round, every state change, every ticket, every proposed fix and every issued report.

It exists in two interchangeable forms — one that keeps everything in memory (store.Memory, used by the demonstration) and one that uses a real database (store.Postgres). Both are held to the same test suite so they cannot behave differently.

Two of its rules are worth knowing. When several tools report the same problem, it merges their reports into one view rather than picking a winner. And it owns the rule that absence is not resolution: a finding that an inspection failed to see is only marked resolved if that inspection actually succeeded (store.PlanReconcile).

Takes in
Raw findings, inspection outcomes, decisions, tickets, reports.
Puts out
The merged, current view of every finding, and the history behind it.

Running the rounds

internal/orchestrator

The conductor

It decides which repositories to inspect, dispatches the work, keeps track of what is in flight, and runs each stage of the pipeline in order.

It is the only part of the program allowed to change a finding’s state. It also performs the housekeeping that stops work getting silently lost: reclaiming jobs from crashed workers, retrying tickets after an outage, and sweeping up findings that look busy but that nothing is actually working on. Every one of those recoveries records why it fired, so a problem that keeps self-healing is visible rather than absorbed.

Its named stages (each is a “pass”) are: Sweep (inspect), EnrichPass (add outside context), TriageAndRoute (explain, score, decide), TicketPass (raise tickets), RemediationPass (attempt fixes), ReconcilePullRequests (check on proposed fixes), SyncFleet (check which repositories still exist).

Takes in
The list of repositories, and a budget for how many outside calls it may make.
Puts out
A completed round, with everything it did and failed to do recorded.

Deciding

internal/triage

Explanation

Asks a language model to explain each finding in plain words — what it is, what the impact could be, how to fix it — and stores that explanation.

Two deliberate limits. The model’s explanation is never allowed to set the priority; that is computed arithmetically elsewhere. And the program keeps working if the model fails: a finding with no explanation is still scored and still routed.

Takes in
Findings that are new or have come back.
Puts out
A written explanation attached to each finding.

internal/score

Priority

Turns each finding into a priority band (P0 to P3) using a fixed formula, so two identical findings always get the same answer.

The formula declares five inputs: the base severity, whether the flaw is known to be exploited, how likely exploitation is, whether the vulnerable code is actually reachable, and how important the repository is. When an input is missing, the score says so next to the number rather than quietly treating the missing input as a zero.

Takes in
A finding’s severity, exploitation context, reachability, dependency type, and the repository’s importance tier.
Puts out
A priority band, the arithmetic behind it, a deadline (SLA) status, and a note naming any input that did not answer.

internal/policy

The decision table

Applies the written decision table: given this finding, in this repository, in this state — fix it automatically, raise a ticket, escalate it, wait for an upstream fix, or deliberately do nothing.

If no rule matches, it fails loudly rather than guessing. A gap in the table is reported as a gap.

Takes in
A finding, the repository’s profile, and what is already in progress.
Puts out
A decision, plus the number of the rule that made it, so any decision can be traced back to the table.
Code vs. spec

The design document (VM-AD §10) numbers nine rules. The decision engine implements rules 1–8. Rule 9 — the limit on how many fixes may share one pull request — lives in the fix-grouping code (remediate.Group) instead, because it is a decision about batching rather than about a single finding.

Fixing

internal/remediate with remediate/guard

The mechanical fixer

For an out-of-date dependency it works out the version that actually closes the flaw, makes the change, proves it, and opens a pull request for a person to review.

The order is fixed and the proof is the point: it checks the repository builds before it changes anything (so it is not blamed for pre-existing breakage), makes the change, then re-runs the inspection tools to confirm the problem is gone. A change that builds and tests cleanly but does not remove the finding is rejected. It never merges its own work.

The guard is a separate safety check that runs on the actual files on disk, every time, before anything is pushed. It blocks changes to protected paths (build pipelines, ownership files, infrastructure definitions), blocks anything that merely silences a warning, and blocks anything that looks like a password. It reads the files rather than trusting any account of what was changed.

Takes in
A group of findings to fix, and a copy of the repository.
Puts out
A pull request, or a recorded reason why not.

internal/remediate/agent with internal/sandbox

The model-written fixer

The same machinery, but with a language model writing the change instead of a version bump — for problems in the repository’s own source code rather than in its dependencies.

The design point is that the model is structurally unable to misbehave rather than asked not to. It cannot reach the safety guard, cannot see the credential, and cannot reach the network or write outside its working copy — those limits are imposed by the surrounding harness. The sandbox does not assume it is closed: it actively tests its own boundaries with harmless probes before any model runs, and refuses to start if a probe did not run or did not block.

There are extra checks for the ways a model can appear to succeed: deleting the test that objected, marking a test as skipped, or reporting a fix it did not make. All of them are checked against the files, not the model’s account.

Takes in
A finding, a working copy, a time-and-cost budget.
Puts out
A changed working copy and a report — or a refusal.

Shared components across the fleet

internal/firstparty

Waves

Handles the case where the flaw is in a component the organisation wrote itself, and several of its own repositories depend on it.

Fixing it once fixes it everywhere, but only in the right order: first the shared component, then the repositories that use it. This piece works out who is affected, and keeps two numbers separate — how many repositories depend on the component, and how many actually reach the vulnerable code. It also identifies repositories a fix cannot help (because they point at a local copy), so they are flagged for a person instead of being counted as done.

Takes in
The dependency lists gathered during inspection, and a register of which components the organisation owns.
Puts out
A “wave” — the upstream fix, the affected repositories, and the steps that clear it.

Outside context

internal/feed

Exploitation context

Asks the exploitation catalogues two questions about each vulnerability: is it known to be exploited in the wild, and how likely is exploitation.

It is careful about not knowing. An identifier the catalogue has never heard of is recorded as unanswered, which is a different fact from measured as harmless. Answers that cannot be true (an impossible probability, a date in the future) are discarded rather than repaired. An old answer is used and labelled with its age rather than thrown away.

Takes in
The identifiers of the findings currently open.
Puts out
Exploitation context, each answer marked with its date, and a record of which questions nobody answered.

Telling people

internal/tracker

Tickets

Creates and updates tickets in whichever issue tracker the organisation uses — GitHub Issues, Jira or Linear.

Its main job is not creating tickets but not creating duplicates: before opening one it checks its own records and then asks the tracker itself, so a lost record does not produce a second ticket for a problem someone is already working on. If the tracker is down the work is queued and retried automatically, and the round continues — a third-party outage does not become a gap in the inspection.

Takes in
Findings that policy decided need a person.
Puts out
Tickets, comments and closures in the tracker, and a link on each finding.

internal/report

The written report

Produces the written report for a round: the headline counts, what changed since last time, the coverage position, and the caveats.

Each report is fixed at the moment it is issued, stamped with a fingerprint of its own contents, and stored. That means a number quoted in a meeting months later can be traced back to the exact round it came from and checked against the original. Reports are also redacted by audience: the widest-circulated version carries counts and coverage but no finding detail.

Takes in
A completed round.
Puts out
A stored, unchangeable report in both machine and human-readable form.

internal/gh

The code host

Everything that talks to the code host (GitHub): which repositories exist, cloning them, pushing branches, opening pull requests, receiving notifications when a pull request is merged, and publishing reports to an archive.

The notification path is the primary way the program learns a fix was merged. It verifies each notification cryptographically, ignores repeats, and ignores messages that arrive out of order. A slower fallback checks anything the notifications did not cover — and if no notification has arrived at all for a while, the program treats its own notification path as broken, falls back to asking directly, and says so rather than going quiet.

Takes in
Notifications from the code host; requests from the rest of the program.
Puts out
Branches, pull requests, published reports, and the current state of proposed fixes.

The interface

internal/api

The service layer

The service the web interface talks to. Twenty addresses covering findings, rounds, coverage, repositories, shared-component waves, trends and reports.

Three properties are enforced here rather than left to the interface. Searching and filtering happen on this side, so the browser never has to download everything. No response may contain anything shaped like a password — a response that does is refused, not cleaned up and sent. And the shape of every response is published in a machine-readable form, from which the interface’s own definitions are generated, so the two cannot drift apart.

Takes in
Questions from the interface.
Puts out
Answers, each carrying its own caveats.

reportui/ the web interface

The screens

A searchable finding explorer, a detail page per finding, a per-round overview, coverage, repositories, shared-component waves, history and trends, and the list of issued reports.

It is built to preserve distinctions rather than tidy them away. A missing exploitation score reads “not looked up”, never 0.00. A finding the last inspection did not see is marked, with an explanation that this is ambiguous. A number computed from partial information carries its caveat beside it, so the caveat survives being copied into an email. Every count links to the list that produced it, so any figure on screen can be checked by clicking it.

Takes in
Answers from the API.
Puts out
The screens a person reads.
Code vs. spec

The interface specification (VM-UI §7.1) names three off-the-shelf libraries for routing, tables and styling. None of the three is installed. The routing and the tables are hand-written and the styling is plain CSS; only the list-virtualisation library from that family is used. Two specified features are also absent: saving a filter for reuse, and logging who looked at what.

Keeping the program honest

internal/audit

Producer coverage

A test suite that inverts the usual question. Instead of asking “is this field displayed?”, it asks “does any real code actually write this field?” — and answers by running the real pipeline and looking at what comes out.

It exists because the same defect kept recurring: a piece of information that something reads and nothing writes. It looks identical to a feature nobody has used yet, and no ordinary test catches it, because tests supply the value themselves. This check found eleven instances during the build.

Takes in
The output of a real pipeline run.
Puts out
A pass, or a list of fields nothing produces.

internal/demo

The demonstration

It contains invented inspection results — invented repositories, invented vulnerabilities — in a single clearly-labelled file, and then feeds them through the real pipeline.

Nothing in it writes a finding, a priority or a state directly. That is deliberate: a demonstration that made up its own conclusions could show something the real program cannot produce.

Takes in
The invented tool output.
Puts out
A fully populated system, with the awkward cases present on purpose — a failed inspection, a problem that came back, a deadline breach, a shared-component wave.

cmd/apiserver · cmd/orchestrator · cmd/scanworker

The runnable programs

The three things you can actually start: the service behind the web interface, the conductor, and the inspection worker.

Code vs. spec

Four further command folders exist and are empty — cmd/fixworker, cmd/bumpworker, cmd/triage and cmd/vfctl (the command-line tool the specs describe for operators). The fixing and triage logic is fully built and tested as a library, but nothing yet runs either on a schedule, and there is no operator command line.

03How data flows

One finding’s journey, end to end. These sixteen steps are a real sequence — each one depends on the one before it.

  1. A round begins. The conductor (orchestrator.Sweep) works out which repositories are in scope, checks it has enough budget for outside calls, and dispatches an inspection job for each. Every repository it planned to inspect is recorded now, so one that is never reached cannot vanish silently.

  2. A repository is inspected. A worker takes a copy of the repository and runs each applicable tool over it. Say govulncheck reports that a networking library has a known flaw. The worker also reads the repository’s dependency list while the copy is on disk.

  3. Tool output is translated. The matching adapter turns that tool’s output into the program’s own vocabulary: the identifier, the affected component, the current and fixed versions, the severity, and whether the vulnerable code is actually reachable.

  4. Duplicate reports are merged. Two tools often report the same vulnerability under different names. The program builds a table of equivalent identifiers from the tools’ own published cross-references and collapses them into one finding (scan.AliasTable). The result is given its stable identity (fingerprint.Compute).

  5. It is recorded. The store keeps each tool’s report separately and builds one merged view from them (store.Project). If this identity has been seen before, this is a new sighting of an existing finding; if not, it is newly DETECTED.

  6. Outside context is added (orchestrator.EnrichPass). The exploitation catalogues are asked about this vulnerability’s identifiers — including its alternative names, since the catalogues use different ones. An answer is stored with its date. No answer is stored as no answer.

  7. It is explained (orchestrator.TriageAndRoute). A language model writes a plain description, the likely impact and a suggested remedy. The finding moves to TRIAGED.

  8. It is scored (internal/score). The formula produces a priority band and a deadline. If the exploitation catalogues did not answer, the score carries a note saying which inputs are missing and that it should be read as a floor.

  9. A decision is made (internal/policy). The decision table is consulted. Say this is a minor version bump, in a repository that has a test suite: the decision is fix it automatically, recorded with the number of the rule that decided.

  10. A ticket may be raised (orchestrator.TicketPass). High-priority findings get their own ticket; lower-priority ones are gathered into a single ticket for the whole round, so the tracker is not flooded.

  11. A fix is attempted (orchestrator.RemediationPass). The repository is locked so two fixers cannot collide. The finding is claimed, and only then does it move to AUTO_REMEDIATING — that state always means a worker is genuinely holding it. The fixer checks the repository already builds, applies the version bump, and then the guard inspects the resulting files.

  12. The fix is proved. The tools are re-run. Only if the finding is genuinely gone — and the build and tests still pass — is a branch pushed and a pull request opened. The finding moves to PR_OPEN. If the bump resolved to a lower version than needed (a real and common occurrence), the re-inspection still sees the finding, the whole branch is discarded, and the finding goes to a person.

  13. A person reviews and merges. The program never merges its own work.

  14. The merge is noticed. The code host notifies the program, which moves the finding to MERGED. That is deliberately not “fixed”: a merge is a statement of intent, not evidence.

  15. The next round proves it. The repository is inspected again. The finding is not reported this time, and the inspection completed successfully — so it becomes VERIFIED, attributed to this program’s own merge. Had the inspection failed or only partly run, the finding would have stayed exactly where it was, marked as not re-observed.

  16. It appears in the report. The round’s report is generated, fixed, fingerprinted and stored, and the interface can show that round’s position as it stood then — not as it looks today.

Where the journey branches

  • A password is found. Step 9 short-circuits. A secret is escalated immediately whatever else is true, gets its own ticket regardless of priority, and is never batched — because the remedy is a person rotating a credential, and batching delays it. No automated fix is attempted. The value itself never enters the system at any point.

  • No test suite. No automated fix is attempted, whatever the decision table says, because there would be no way to prove the change worked. The finding goes to a person and the interface says why.

  • The flaw is in a shared internal component. The finding waits (BLOCKED_UPSTREAM) on the upstream fix rather than each repository opening its own pull request. If the wave cannot advance a particular repository — because it points at a local copy — that one is routed to a person instead of waiting forever for something that has already happened.

  • No fix exists yet. The finding is parked as blocked, with the reason recorded. Notably, the program distinguishes “nothing to do” from “tried and failed”: a fix that applied, built, passed tests and still did not remove the problem gets its own reason code, and unlike the former it does not pause the deadline clock.

  • A person rejects the pull request. The finding becomes DECLINED and is never automatically re-attempted. Only a human can put it back in the queue.

  • The inspection fails. No finding in that repository is verified by that round. Its findings are marked not re-observed, the gap is recorded with a cause and an owner, and the round’s report states that its numbers are lower than the truth rather than better.

Where it loops back

  • A verified finding reappears. A later inspection sees it again. It becomes REGRESSED — deliberately a different state from a new finding, because it means something undid a fix, which is a different problem.

  • A merged fix did not work. The post-merge inspection still sees the finding, so instead of being verified it returns to TRIAGED and goes round again.

  • A fix attempt crashes. The claim expires and the finding returns to the queue by itself. If something leaves a finding looking busy with nothing working on it, a sweep finds it and returns it, recording why.

  • A pull request is forgotten. If a pull request’s record is lost, the finding returns to the queue; re-planning produces the same branch name, which the fixer recognises and adopts rather than opening a second pull request.

Counted by distinct external system or artefact the program reads from. The code host is counted once even though it supplies three different kinds of information, because it is one system with one set of credentials.

a · Scanners — nine tools that inspect code and produce findings

All nine are real: real translators, run as real programs (internal/scan/runner starts an actual process). What is missing is the tools themselves, which are not installed here — so no finding in the demonstration came from one. Each was built and tested against genuine captured output from the real tool, kept in testdata/fixtures.

All nine are read-only. The inspection worker deliberately holds no credential that would let it write to any repository.

Go dependency flaws, and — uniquely — whether the vulnerable code is actually reachable from this repository.

osv-scanner

Dependency flaws cross-checked against the open vulnerability database; catches what reachability analysis skips.

gosec

Insecure patterns in Go source code, such as weak randomness or unsafe handling of credentials.

staticcheck

Correctness problems in Go source, filtered to the security-relevant subset.

gitleaks

Passwords, keys and tokens committed into the code. Reports the kind of credential and where it is, never the value.

trivy

05What’s real vs. pretend right now

This map describes a program that is complete and demonstrable, but has never run against a real repository. The distinction matters, and FINAL-STATUS.md covers it in full. The short version:

Genuinely working, end to end, with no credentials

The vocabulary and identity rules, the nine translators (against real captured tool output), both forms of memory, the state machine, the conductor and all its stages, scoring, the decision table, the mechanical fixer and its safety guard, the shared-component waves, the ticket logic, the report generator, the API, and the web interface. The demonstration exercises all of it.

Present as a design, with a deliberately hostile stand-in behind it

The language model that explains findings, the language model that writes fixes, the exploitation catalogues, and the code host. “Hostile” means the stand-ins were written to behave worse than the real thing — opening duplicate pull requests, rejecting pushes, rate-limiting, serving stale data, returning answers that cannot be true — so the program is tested against the awkward cases rather than the convenient ones.

Not built at all

The real build-and-test toolchain (so “this fix works” is currently the stand-in agreeing with itself); any live connection to GitHub; any live exploitation feed; a scheduler to run the fixer automatically; access logging; and the ability to generate a report from the interface.

Built but unproven

The sandbox that confines the model. Its real implementation exists, but every test of it runs against the stand-in, because this machine is a Mac and the real one needs Linux. Until a Linux test proves its boundaries actually hold, no API key should reach any machine that runs it.

Three smaller honesty notes

Since the map above would otherwise imply more than is there:

  • A finding’s location is recorded down to the file, not the function — no inspection tool in use reports the enclosing function. This means verifying one problem in a file could hide a second one in the same file, and the program says so whenever that is possible.
  • Tool versions are recorded per round, not per finding.
  • Comparing two rounds reports what appeared and what disappeared exactly, but not what changed state — reconstructing a finding’s state as of a past round has not been built.
